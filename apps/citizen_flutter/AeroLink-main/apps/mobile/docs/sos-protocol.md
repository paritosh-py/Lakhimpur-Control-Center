# SOS chat and acknowledgement protocol

## Flash both nodes

Open firmware/personal_node/personal_node.ino and
firmware/base_station/base_station.ino as separate Arduino sketches.
Install the Arduino-ESP32 board package (3.x) and ArduinoJson (7.x), select the
actual ESP32 board/port and upload each sketch to its respective board.
Arduino CLI/boards were not available for a hardware build in this workspace.

The personal node advertises AeroLink-Test. Pair/connect through the app's
AeroLink device screen. Base SSID: CodeRed_SOS_Network (open prototype network).
Base address: 192.168.4.1. Base receives UDP 4330; personal node binds UDP 4331
and forwards replies as BLE notifications.

Both sketches and this app must be upgraded together. The original personal
node never listened for UDP replies. The original ACKs also lacked sosId and
messageId, so they cannot safely update the new request lifecycle.

The sketch uses Espressif's BLE server/notification APIs and ArduinoJson 7
serialization APIs:
- https://docs.espressif.com/projects/arduino-esp32/en/latest/api/ble.html
- https://arduinojson.org/v7/api/json/deserializejson/
- https://arduinojson.org/v7/api/json/serializejson/

## Framing and identifiers

The service/write/notify UUIDs are unchanged from the original firmware.
BLE transfers contain a leading newline (resynchronization), compact JSON, and
a trailing newline, split into chunks of at most 20 bytes. Receivers accumulate
bytes before decoding UTF-8, so non-ASCII text can span BLE chunks.
UDP transfers contain one complete JSON object, without BLE framing.
Maximum UDP JSON size is 1024 bytes; the app reserves one byte for its delimiter.
Chat text is limited to 600 UTF-8 bytes and the complete packet size is also checked.

Every packet carries sosId. Requests use SOS- plus 24 random hexadecimal digits.
Retries preserve the SOS ID, payload and original timestamp.
messageId correlates an individual operation. Chat retries reuse the message ID
to let receivers deduplicate. Authority messages need unique message IDs; repeat
the same ID when retrying the same message. Missing IDs in Serial commands are
generated by the base station.

## Packet examples

Substitute the actual SOS ID printed by the app/base station.

Phone sends SOS (other form fields remain supported):

    {"type":"SOS","sosId":"SOS-...","messageId":"MSG-...","timestamp":"2026-09-05T10:00:00Z","latitude":18.5,"longitude":73.8,"peopleAffected":2,"conditions":[],"additionalDetails":"Need help"}

Personal-node receipt:

    {"type":"ACK","status":"SOS_RECEIVED","sosId":"SOS-...","messageId":"MSG-..."}

Base-station receipt (the personal node forwards this unchanged):

    {"type":"ACK","status":"BASE_STATION_RECEIVED","sosId":"SOS-...","messageId":"MSG-..."}

Victim chat and base receipt:

    {"type":"CHAT","sosId":"SOS-...","messageId":"MSG-...","sender":"victim","text":"We have moved upstairs"}
    {"type":"ACK","status":"CHAT_RECEIVED","sosId":"SOS-...","messageId":"MSG-..."}

In the base station Serial Monitor (115200 baud, newline), send:

    {"type":"CHAT","sosId":"SOS-...","messageId":"authority-chat-1","text":"Stay upstairs. Help is on the way."}

The base adds sender: authority and unicasts to the node registered for this SOS.
The console prints victim messages; repeated messageId values represent retries.
A UDP send alone does not prove the victim received an authority message.
Resend the same message ID if needed; the app deduplicates it.

To request closure, send:

    {"type":"COMPLETION_REQUEST","sosId":"SOS-...","messageId":"closure-1"}

The app opens a popup, including when another app page/chat is visible.
"Review later" leaves the request open and exposes a review button on the card.
The victim can answer "I still need help" or "Yes, complete request":

    {"type":"COMPLETION_RESPONSE","sosId":"SOS-...","messageId":"MSG-...","requestId":"closure-1","resolved":false}

The base records the decision and replies:

    {"type":"ACK","status":"COMPLETION_RESPONSE_RECEIVED","sosId":"SOS-...","messageId":"MSG-..."}

Only a true decision with this reply makes the app show Request completed.
False keeps the SOS open. A new closure request must use a new message ID.
If the reply is lost, retry the same answer: the base repeats its acknowledgement
without applying the decision twice. The app prevents contradictory answers to
an in-flight/uncertain decision.

## Failure behavior and prototype limits

- Local ACK: personal node received the SOS; it does not establish base receipt.
- Base unavailable: local confirmation remains visible; retry preserves the SOS.
- Missing ACK after 20 seconds: delivery remains unconfirmed; retry is available.
- Wrong/missing SOS IDs, duplicate closure requests and out-of-order local ACKs
  cannot close another request or regress acknowledged/completed state.
- Request/chat history lives in app memory only. Keep the app running.
- No offline queue/replay for authority messages while BLE is disconnected.
  Authorities must resend after reconnect. No background notification guarantee.
- The base retains up to 16 request routes in RAM, including closed requests.
  It refuses new routes when full; reboot clears them. This is a bench prototype.
- The Wi-Fi network is open and JSON replies are not cryptographically authenticated.
  SOS IDs isolate conversations but are not authentication.
- The supplied sketches require physical board compilation and round-trip testing.

## Verification

Automated: flutter analyze --no-pub and flutter test --no-pub.

On hardware:
1. Connect phone to personal node and activate SOS. Compare ID/timestamp in the
   card and base console; Confirmed precedes Acknowledged.
2. Turn the base off and send SOS. Verify only personal-node confirmation and
   the unavailable/waiting warning. Turn it on and retry with the same SOS ID.
3. Send victim chat and verify console text plus Received by base station.
4. Send the authority chat JSON above. Verify it appears once, including on retry
   with the same message ID. Test Hindi/Marathi UTF-8 text and long messages.
5. Send a closure request; choose I still need help. Verify resolved:false in the
   console and an open request in the app. Request closure again with a new ID
   and choose Yes. Verify Request completed only after the response ACK.
6. Disconnect BLE, navigate between pages, reconnect and retry unconfirmed chat.
   Check that another SOS ID never affects this request.
